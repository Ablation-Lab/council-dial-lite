# Council Dial Lite: plan

Sections 1 to 3 of the Council Dial Lite skill. The ground rules in SKILL.md apply here too, and SKILL.md says which file holds each section.

## 1. Choose the type

Use what the user asked for. If they didn't say, suggest one of these:

| Preset | Type | Agents |
|---|---|---|
| Standard | specialised reviewers, judged | 6 (3 reviewers, a judge, an appeal, a check) |
| Quick | 3 generalist reviewers, pooled | 4 (3 reviewers, a check) |
| Thorough | specialised reviewers, judged, with debate and a baseline | 10 |

Thorough, and any council with debate, sequential reviewers or a baseline, hasn't been run on Lite 1.4.0 or later, this version included. Whenever you suggest or plan one, say so in one line.

The parts:
- **Reviewers:** specialised (each has a role; by default correctness, security and privacy, docs and policy accuracy; the user can name 1 to 9 others) or generalist (all review everything; 1 to 9, default 3). Clean each role first: trim it, turn every run of spaces, tabs or line breaks into one space, and drop control and invisible characters. A role is then 1 to 60 characters, doesn't start with a hyphen, and has no quotation mark (straight or curly), backtick, comma, or any of `$ ; & | < > * ? % ! { } \`. No two roles may be the same ignoring case.
- **Combine:** judged (a fresh judge verifies and merges), pooled (you list every finding, merging exact duplicates only, and drop nothing; you then check each finding yourself, section 8) or consensus (you keep findings a majority of reviewers raised; needs 2 or more reviewers). Consensus with specialised or sequential reviewers keeps few findings, because reviewers rarely raise the same one; say so.
- **Brief version:** Lite builds brief version 3 unless the user asks for version 2, the wording of runs before Lite 1.3.0, so they can be compared with those. In version 3 the judge numbers its merged findings M1, M2, sets each severity itself and gives one of five rulings (REAL, PARTLY REAL, OVERSTATED, UNDERSTATED, NOT REAL), and the appeal checks severities as well as dismissals.
- **Running code:** by default nobody may run anything. In version 3, every agent is then the plugin's read-only agent, `council-dial-lite:council-reader`, which has only the Read, Grep and Glob tools, so it can't run anything or write any file, and the rule is enforced and not just written in the briefs. Only if the user allows running code, start the council's agents as general-purpose agents, and tell each one the user allowed running code. Version 2 runs always use general-purpose agents, as they did before. A general-purpose agent has every tool the session allows, writing, editing and web tools included, not only a shell. The check only compares text, so it's always the read-only agent, unless the plugin's agent is missing and the user agrees to go on with general-purpose agents (section 4): then the check is general-purpose too. Whenever any agent will be general-purpose, say so when you ask for the yes (section 2), naming which and that they have every tool the session allows.
- **Appeal:** on by default for judged; the user can turn it off. After the judge, one fresh agent sees only the findings the judge marked NOT REAL, with the judge's reasons, and flags any it thinks were wrongly thrown out; in version 3 it also checks severities (section 4). It doesn't overrule the judge: the user makes the call. In version 2 it runs only if the judge throws a finding out, and in version 3 also if there's a severity to check; say so when you count it.
- **Extras:** debate (one round where each reviewer's seat answers the others' findings; needs 2 or more reviewers), sequential (reviewers go one at a time, each seeing the earlier reports), baseline (one extra reviewer working alone, started with the reviewers, for comparison).
- **Check:** every Lite run ends with one check agent (section 6), except a raw run.
- **Raw mode:** only if the user asks for a raw run. The council runs exactly as it otherwise would, and every brief and report is saved, but no check agent runs and you don't write the summary, the counts, the severity list or the comparison table. Instead you write a hand-off file in the run folder (section 10), so the user can give the folder to a fresh agent, perhaps on a stronger model, to do the analysis and bookkeeping. A raw run has one agent fewer than the same type otherwise would (no check); say so when you count. Its label has `+raw` after the other extras (below), so raw runs are estimated and compared only with raw runs. With no check agent, no agent compares the briefs with their templates or checks the overview either; say so.
- **Seats:** every agent sits in a seat: each reviewer (named by its role, or `reviewer <k>` for generalists), the judge, the appeal, the baseline reviewer and the check (not in a raw run). A reviewer's debate turn sits in its reviewer's seat.
- **Model:** the user can pick `sonnet`, `opus`, `haiku` or `fable` for every subagent, for all the reviewers, or for one seat. For each seat, its own choice wins, then one for all reviewers (for a reviewer's seat), then one for every subagent. Pass the seat's model as the Agent tool's `model` on its agents' calls; for a seat with none, leave `model` out and it inherits this session's model. The Agent tool takes only those four aliases. If a seat's model isn't this session's, say it runs at that model's default effort level unless an effort is set for it. Record your own model id, the one your system prompt gives, as `models.main` when it starts with `claude-` and has only lower-case letters, digits, dots and hyphens, optionally ending in `[1m]`; otherwise record `null` and tell the user in one line. You can't see `CLAUDE_CODE_SUBAGENT_MODEL` or `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`: ask the user only if they mention them, and record what they say as `models.env` (an alias or a model id of the form above) and `models.force` (`true` only if `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` is `1` or `true`).
- **Effort:** set only if the user asks: `low`, `medium`, `high`, `xhigh` or `max`, for every subagent, for all the reviewers or for one seat, with the same precedence as for models. Pass it as the Agent tool's `effort` parameter, the per-call route Claude Code supports (2.1.292 or later); leave it out for a seat with none. A level a seat's model doesn't support runs at the highest level it supports below that. A seat with no effort runs at this session's level on this session's model, and at its model's default on another, unless `CLAUDE_CODE_SUBAGENT_EFFORT` is set (below).
- **Saved effort levels:** a seat with no effort set, on another model than this session's, runs at the level saved for that model in the settings files (`modelSettings`, or a top-level `effortLevel` that applies to it), and only otherwise at the model's default. Only when at least one seat runs on another model than this session's (and has no effort set), search the project's `.claude/settings.local.json` and `.claude/settings.json` (if they exist) before the run with Grep, for `effortLevel`, showing matching lines with one line of context before each (so a `modelSettings` entry shows which model it's for). Never Read those files: their `env` block can hold secrets. When every seat is on this session's model, don't search them, since no saved level can apply, and that isn't a deviation. Use only the `modelSettings` and `effortLevel` values Grep shows, and show each such seat's level and where it comes from. Lite doesn't read the user's or managed settings, which are outside the project, so say a level saved there may apply.
- **What Lite can't see:** it can't read the session's effort level (logged as `null` in the top-level `effort`), `CLAUDE_CODE_EFFORT_LEVEL`, or `CLAUDE_CODE_SUBAGENT_EFFORT`, which (from Claude Code 2.1.316, by Claude Code's changelog; its environment-variable reference doesn't list it) sets the effort of every subagent that nothing else names one for, in place of the level it would otherwise get; ask the user only if they mention it, and if it's set, say each seat with no effort runs at that level. Whenever any seat has an effort set, tell the user, before you start any agent, that `CLAUDE_CODE_EFFORT_LEVEL`, if it's set in their shell or in a settings file's `env` block, overrides every seat's effort, and that they can check the shell with `$env:CLAUDE_CODE_EFFORT_LEVEL` in PowerShell or `echo $CLAUDE_CODE_EFFORT_LEVEL` in bash, and the settings files' `env` blocks by looking.
- **Blind:** models and effort go only in the Agent tool's parameters, never in a prompt; only `run.json` records them.

The largest custom council is 22 agents with the check (21 in a raw run). Agree what's being reviewed in one line: the material's paths, any out-of-scope exclusion, and only words the user gave (ground rules). Trim it, turn every run of spaces, tabs or line breaks into one space, drop control and invisible characters, and keep it to 600 characters (the character rules for roles don't apply to it). Don't describe what a file is. If anything next to it is out of scope, such as a folder of sample data, say so in the same line, such as `shelfkeep.py, scripts/tidy.sh and README.md; not the shelves/ folder (sample data)`: this line is the only description of the target the briefs get, so an exclusion you only tell the user doesn't reach the agents. Never say it has planted, deliberate or known problems (even for a sample), or mention an answer key or expected findings, because that changes how the reviewers review it. Don't put secrets or private details in it; it's stored in the log.

**The label.** Build it from the type, `briefVersion`, the models, `runningCode` and `liteVersion`, never from a stored label:
- Start with `lite: `, then `specialised` or `generalist`, a hyphen and the number of reviewers.
- For specialised reviewers whose roles, ignoring order and case, aren't exactly the three defaults: a space, then `[`, the roles in lower case sorted by character code (a space before a hyphen, before digits, before letters) and joined by `, `, then `]`.
- Then `/`, the combine method, and `+debate`, `+sequential`, `+appeal`, `+baseline`, `+running-code` and `+raw` for each one the run has, in that order: `+baseline` when `type.baseline` is `true`, and `+running-code` when `runningCode` is `allowed`. A run logged before Lite 1.6.0 has no `type.raw`, and isn't raw; one with no `runningCode` didn't allow it.
- Then, for brief version 3, a space and `v3` (version 2 runs have nothing here).
- Then the seats, from `type.seats`. Each seat's model is `models.env` when `models.force` is true, or else the alias asked for that seat, or else `models.env`, or else `models.main`, or else `inherit`; follow it with `/` and the seat's effort if one was asked for. If every seat has the same model and effort: a space, `@` and that, or nothing if it's `inherit` with no effort. Otherwise: a space, `@{`, the seats as `<seat>=<model>` joined by `, `, and `}`. The reviewers come first, as one `reviewers=…` if they all match, or else each by its role in lower case (sorted as above) or as `reviewer <k>`; then `judge`, `appeal`, `baseline` and `check` for those the run has.
- Last, a space and `(Lite <liteVersion>)` from the run's `liteVersion`, such as `(Lite 2.2.2)`, so estimates and comparisons never mix runs of different Lite versions. Rebuild an older run's label with its own `liteVersion` the same way.
- A run logged before Lite 1.2.0 has no `type.seats`: every seat had the alias the user picked for every subagent (`models.requested`), and no effort. From 1.2.0, `models.requested` is the alias the user set for every subagent, if they set one, and otherwise `null`; the seats hold the rest.

For example: `lite: specialised-3/judged+appeal v3 @claude-opus-5-5 (Lite 2.2.2)`, `lite: specialised-2 [api, perf]/judged+debate+appeal v3 @sonnet (Lite 2.2.2)`, `lite: generalist-3/pooled @sonnet/high (Lite 1.2.0)`, `lite: specialised-3/judged+appeal v3 @{reviewers=sonnet, judge=haiku, appeal=opus/max, check=claude-opus-5-5} (Lite 2.2.2)`, `lite: specialised-3/judged+appeal+raw v3 @claude-opus-5-5 (Lite 2.2.2)`, `lite: specialised-3/judged+debate+appeal+baseline v3 @claude-opus-5-5 (Lite 2.2.2)`, `lite: generalist-3/pooled+running-code v3 @sonnet (Lite 2.2.2)`, or `lite: generalist-2/consensus v3 (Lite 2.2.2)`.

## 2. Estimate, then ask

Read each `run.json` in the Lite folder whose `edition` is `council-dial-lite` and whose label, rebuilt from its `type`, `briefVersion`, `models`, `runningCode` and `liteVersion`, is this label. A run counts when its `results` are logged and every agent in the top-level `agents` list whose `started` isn't `false` has `tokens` (so an appeal that didn't run doesn't count against it; in runs logged before Lite 1.1.0, which have no `started`, an appeal whose `results.appeal.ran` is `false` doesn't either). If any runs count, the estimate is the average of their total tokens over all of them, with the lowest and highest and how many runs it's based on. Also name the latest 5 of them by planned date and then run id, or all of them if there are fewer; the estimate still uses every run that counts. If it's based on one run, say so. Start the plan with a line or two giving the type, the agent count and the estimate, and saying that bigger material costs more, because every reviewer reads all of it. The rest of the plan, below, follows them, including the Lite folder notice (section 3) if this run will create the folder. Then give one line per seat, in this exact wording, the same in every run, raw or not:
- `<seat>: model <alias> (set for this seat)`, `(set for all the reviewers)` or `(set for every subagent)`; or, with none set, `<seat>: model not set, so it inherits this session's model (<models.main, or "unknown">)`. If the user told you `CLAUDE_CODE_SUBAGENT_MODEL` is set, write `model not set, so it runs on <models.env> (CLAUDE_CODE_SUBAGENT_MODEL)` for a seat with none set, and when `models.force` is true, `model <models.env> (forced by CLAUDE_CODE_SUBAGENT_MODEL_FORCE)` for every seat.
- Then, after `; `: `effort <level> (set for this seat)`, `(set for all the reviewers)` or `(set for every subagent)`; or, with none set: on another model, `effort not set, so it runs at <level>, saved for that model in <file>` when section 1 found one; otherwise, if the user told you `CLAUDE_CODE_SUBAGENT_EFFORT` is set, `effort not set, so it runs at <level> (CLAUDE_CODE_SUBAGENT_EFFORT, unless a level saved where Lite can't read applies)`; otherwise, on this session's model, `effort not set, so it runs at this session's level, which Lite can't read`; and on another model, `effort not set, so it runs at that model's default, unless a level is saved for it in your user or managed settings, which Lite doesn't read`.

Then show the one-line description of what's reviewed on a line of its own, `Description every brief will get: <description>`, say it goes word for word into the brief of every agent of this council that gets it (name them for this type: its reviewers, and its debate agents, judge and baseline reviewer if it has them; the appeal never gets it, and the check sees it only inside the saved briefs it compares) and is all the council's prompts say about the target apart from its paths (Claude Code adds some context of its own, which the README's Limits list), and ask the user to confirm or change it, together with the yes.

- **Agents:** one line saying which agents are the read-only agent (Read, Grep and Glob only) and which, if any, are general-purpose, with every tool the session allows (section 1).
- **No history:** say there's no estimate for this type yet. Suggest a smaller trial run first (a Quick council, or this council on one part of the material; when the council asked for is already Quick, only this council on one part of the material) only when the material is more than 5 files or names a whole folder; for up to 5 named files, say a trial isn't needed.
- **The material looks large** compared with what those runs reviewed: say the estimate is likely low and suggest the same smaller trial. Judge this from the user's description and the file list; don't open the files to size them (see the ground rules).
- **Tokens only.** Never turn tokens into money. If the user asks about cost, point them to Anthropic's pricing page.
- **Raw runs:** a raw run counts here only once it has been analysed (its `results` are logged). The estimate covers the council's agents only, not the later analysis, whose tokens Lite never sees; say so.

Then wait for the user's yes.

## 3. Make the plan

**The Lite folder.** Before creating anything, check that no folder on the way from the project root to the Lite folder, the Lite folder included, is a symbolic link or junction. The project root itself isn't checked: it's the folder the user started in, and everything is written inside it. File tools can't tell a link, so use the session's shell tool, one command per folder, exactly in this form and with nothing else in the command (text Claude Code shows with it, such as its description, doesn't count). Both forms ran without a permission prompt in Claude Code's default mode in our tests, where other forms asked once per folder:
- **PowerShell:** `Get-ChildItem -LiteralPath '<parent>' -Force -Filter '<name>' | Select-Object Name,Mode,LinkType`. `<parent>` is the full path of the folder above the one you're checking, with no slash at the end, and `<name>` that folder's name alone, with no slash. It prints one line for an item of that name, or nothing at all, and no error, when there's none: only that empty output means the folder doesn't exist. Stop and tell the user if the line's `LinkType` isn't empty, if its `Mode` ends in `l` (such as `d----l`, which marks any link, even one whose `LinkType` is blank), or if its `Mode` doesn't start with `d` (a file, or a file-type link, with that name).
- **Bash:** `ls -ld -- '<folder>'`, with the folder's full absolute path and no slash at the end (a trailing slash follows a link). A link's line starts with `l` and shows `->`. Only "No such file or directory" means it doesn't exist.

In either shell, a line in Claude Code's own form `Shell cwd was reset to <folder>` isn't the command's output: leave only that line out when deciding whether the command printed nothing, or only "No such file or directory". Any other text, on its output or its errors, is the command's. If a check command is refused, needs a permission you can't get, or fails in any other way, stop and tell the user: never treat that as "doesn't exist". In our tests these exact forms ran without a prompt, including on a junction. A PowerShell command on a link's own path was refused (Claude Code resolved the link to its target outside the project), and so was a Bash command with a relative path. A subexpression such as `(Get-Item …).LinkType` asked for permission.

Check the folders in order from the top, starting with the one just below the project root (such as `reviews`, listed from the project root), then the next (such as `lite`, listed from `reviews`). Stop at the first that doesn't exist: it and those below it will be created as plain folders, so don't check them. Inside the single quotes, write each `'` in a path as `'\''` in Bash, or as `''` in PowerShell. PowerShell also reads `‘`, `’`, `‚` and `‛` as single quotes: if a path holds one of them, don't use PowerShell for it; use Bash if the session has it, and otherwise tell the user and ask whether to go on without the check. Use the shell for nothing else. If one is a link, stop and tell the user. If the session has no shell tool, tell the user you can't check for links and ask whether to go on.

When agents can run code (the user allowed it, or brief version 2, whose agents are general-purpose), check the run folder and its `reports/` folder the same way before each write into them, since such an agent, still running, could have replaced one with a link.

**Run id and folder.** Lite never reads the clock or makes up random characters; the run id is `lite-`, today's date as 8 digits, a hyphen and a two-digit number, such as `lite-20261108-01`. Today's date is the one your session context gives (it may be local time rather than UTC). The number is one more than the highest number among that date's existing run ids whose part after the date is 2 or 3 digits, or `01` if there are none, with three digits after `99`. An id whose part after the date is 4 characters, such as `3021` or `a7c2`, doesn't count, even if all 4 are digits. Find the existing runs with a file-name search such as Glob for `<Lite folder>/*/run.json` (a content search such as Grep can skip a git-ignored Lite folder). Then try to Read `<Lite folder>/lite-<date>-<number>/run.json` by its exact path: if it exists, take the next number and try again. Earlier runs may have ids ending in 4 hex characters instead; they're still valid. When you order runs, compare the number as a number. The run folder holds `run.json`, a `briefs/` folder and a `reports/` folder; later, `summary.txt` (in a raw run, `ANALYSE-THIS-RUN.txt`, and `summary.txt` only once the run is analysed). Create it by writing `run.json` (below) straight away.
If this run creates the Lite folder, tell the user once, in one line, that the reports will quote their material, so for a private project they should keep the Lite folder out of git, such as by adding `reviews/lite/` to `.gitignore`. Say it in the plan message (section 2) when the instruction-file search there found no Lite folder; otherwise say it when `run.json`'s write creates the folder. Either is a step this skill requires, not a deviation. Every path you give an agent outside the material line, `<run folder>`, `<Lite folder>`, and the check's file paths and its two folder lines included, is a full absolute path (the check's brief-file names and template files are relative to those folder lines, section 6); the material line gives the material's paths relative to the project root (section 4).

**Agents, labels and files.** In this order:

| Step | Agents | Label |
|---|---|---|
| review | one per reviewer | `reviewer: <role>` (specialised) or `reviewer <k>` (generalist, from 1) |
| debate | one per seat, with debate | the seat's label followed by ` (debate)` |
| combine | the judge, for judged | `judge` |
| appeal | for judged with the appeal | `appeal` |
| baseline | with a baseline | `baseline reviewer` |
| check | always, except in a raw run | `check` |

Each agent's file name is its label in lower case, with every run of characters other than `a` to `z` and `0` to `9` turned into one hyphen, hyphens at the start and end dropped, then `.txt`: `reviewer: security and privacy` is `reviewer-security-and-privacy.txt`. If a role has no letter or digit from `a` to `z` and `0` to `9` (such as one written only in another script), use `reviewer <k>` in its place for the file name, where `<k>` is the reviewer's place in plan order, so `reviewer-2.txt`, and `reviewer-2-debate.txt` for its debate turn; the label stays the role. Its report goes in `reports/` and its brief in `briefs/`, both under that name. Reports, briefs and the summary are plain text files, so links, images and HTML copied from the material never render or load when someone opens them on GitHub or in a Markdown viewer. If two agents would get the same file name, stop and ask the user to rename a role.

**Briefs.** Read the template files the run needs, by name, without listing the folder first (each read can ask the user for permission). Read `${CLAUDE_SKILL_DIR}/check-brief.md` first (in a raw run, `${CLAUDE_SKILL_DIR}/raw-handoff.md`), before any file in `briefs/`. A read's prompt offers to allow reading the folder that file is in for the session, so a prompt for a file in the skill folder itself, such as this one, lets one answer cover `briefs/` and `briefs/v3/` too, where a prompt for a file in a subfolder covers only that subfolder. Then read, in `${CLAUDE_SKILL_DIR}/briefs/`, `shared.md` and `reviewer.md` always, `debate.md` with debate, `judge.md` and (with the appeal) `appeal.md` for judged, and `baseline.md` with a baseline. For brief version 3, read `shared.md`, `judge.md` and `appeal.md` from `${CLAUDE_SKILL_DIR}/briefs/v3/` instead; the other files are the same for both versions. Each template is the text inside a `text` block under a `##` heading; the notes around them say which one each agent gets and what fills each `{{name}}`. Build each brief by copying the right text exactly and replacing each `{{name}}` with its value, once; text you put in is never searched for `{{name}}` again. In short:

- **Reviewer:** `reviewer.md`, `brief` or (sequential) `brief-sequential`, with `{{lens}}` from the opening that fits; `{{what-to-review}}` is `shared.md`'s `what-to-review` with `{{target}}` as the one-line description; `{{rules}}` and `{{format}}` are `shared.md`'s texts.
- **Debate:** `debate.md`'s `brief`, with `{{who}}` from `who-role` or `who-seat`.
- **Judge:** `judge.md`'s `brief`, with `{{reports}}` from `reports` or (with debate) `reports-after-debate`, and `{{severity-rule}}` from `severity-rule`.
- **Appeal:** `appeal.md`'s `brief`, with `{{rules}}`. It never gets the description of what's reviewed.
- **Baseline:** `baseline.md`'s `brief`.
- **Check:** `check-brief.md`'s `brief` (next to this file, not in `briefs/`), with `{{rule}}` built as that file's notes say.

Build each brief just before you start its agent, from the templates. Then, before that agent's Agent call (for agents you start together in one message, before that message; while you build it is fine), compare the brief with the template texts it came from, as you read them above (don't read the template files again), part by part: apart from the filled-in values, every character must be the same. If anything differs, build it again and compare again; if it still differs, don't start that agent: tell the user, and stop. Record each comparison in `run.json`'s `briefChecks` before the Agent call: `{"file": "<agent file>", "matched": true, "firstBuildDiffered": null, "checkAgent": null}`, or, when a first build differed and the rebuilt one matched, `firstBuildDiffered` saying in a few words what differed. Your comparison is by reading, so the check agent compares each saved brief with its templates again (section 6), and `checkAgent` records what it found. The check's own entry, and every entry in a raw run, which has no check agent, keeps `checkAgent` `null`. Save a copy of the brief alone, as you built it here, to `briefs/<agent file>`: not the whole prompt (no first line, material lines or reports). Never read a saved brief back to use it.

`tokenNote` is always the exact text above. `deviations`, `userRequests` and `outsideInstructions` are lists of one-line strings; SKILL.md's ground rules say which goes where. `liteVersion` is this plugin's version, the `version` in its `.claude-plugin/plugin.json`, which is 2.2.2; it's written here so you don't need to read that file, which is outside the skill folder and would ask for another permission. `type.raw` is `true` only for a raw run, whose `seats` and `agents` have no check; `analysis` stays `null` except in a raw run (section 10). `planned` is the run id's date, written `YYYY-MM-DD`. `agents` lists every agent in the order above, the check included (a raw run has none). Set an agent's `started` to `true` in the `run.json` change you make just before its Agent call. For each agent (or each group started together in one message), in this order:
1. Save its brief to `briefs/` (section 3, "Briefs").
2. Make one `run.json` change that sets its `started` to `true`. The same change may hold its `briefChecks` entry.
3. Read `run.json` back, as below. A search or a re-read of reports that a step asks for may also come here; no other write and no Agent call may.
4. Make its Agent call (for agents started together, the one message that starts them all).

`run.json` is created before any brief is saved, so the change that creates it never sets `started` to `true`. If the Agent tool then doesn't start an agent, set `started` back to `false` and say why in its `notes`. An agent that never starts, such as an appeal with nothing to appeal, keeps its entry with `started` set to `false` and `savedBy`, `savedMatchesReply`, `tokens`, `toolUses` and `durationMs` all `null`. Every agent's prompt offers a NOTES: slot at the end (section 4), and a title or headings added to a report don't need noting. So an agent's `notes` is one line on anything else it did that its brief or prompt didn't ask for (such as text outside the NOTES: slot that breaks the format its brief asks for, or a refusal), and anything it left out that they asked for, such as a judge's missing reason line (`OVERSTATED M10 with no reason line`), described in your own words without quoting the material; `null` if nothing.
That includes a finding in its NOTES: slot, the one kind of text there that needs noting, although its prompt says findings go in the report: a problem in the material, or a doubt about whether something in it is right, that isn't one of its report's findings (a remark about the review, such as "Nothing was run", isn't one). Say so in its `notes`, such as `put two findings in its NOTES: slot`. Such an item isn't a council finding, even when the judge or the appeal raised it there: it isn't a merged finding the judge ruled on, and no appeal checked it, so it stays out of the summary, every count and your own checks, and section 7 shows it apart.
`savedBy` is `main session` once you've saved its report (runs from before Lite 1.4.0 can name the agent itself), and `savedMatchesReply` is the result of reading that report back (section 4).
A report's `.as-received.txt` copy (section 4) is never the report: it's kept only as a record. `roles` is `null` for generalists. `seats` lists every seat the type has, in the order of the agents table (a reviewer's debate turn has no seat of its own), with the alias and effort asked for it after the precedence above (`null` for none). Each agent's `model` and `effort` are what you passed to the Agent tool for it (`null` for none), and its `agentType` is the `subagent_type` you passed (`council-dial-lite:council-reader`, or `general-purpose`). `briefChecks` starts empty; section 3 adds one entry per brief. `label` is kept for reading; always rebuild it from `type`, `briefVersion`, `models`, `runningCode` and `liteVersion` when you use it. Change only this run's `run.json`, by its full path; never another run's. You can change it either by reading it and writing the whole file back, or with targeted edits of just the fields you mean to change. After a change, or after a batch of targeted edits made one after another with no other tool calls in between, read the whole file back once, in full, after the last of those edits (later in the same batch of tool calls, or in the next one; a read placed before an edit in the same batch reads the old file), and check that it's valid JSON and that only those fields changed; if it isn't, fix it before you change it again or rely on it.
A read-back, of `run.json` or of any saved file, is one Read of the whole file with no `offset` or `limit`: a read from a line onwards, of some of its lines, or a search such as Grep isn't one. If Read won't return a whole file at once, use the option it offers for that (such as `allow_large`); if it still can't, tell the user, and stop. Unrelated tool calls in the same batch as the read-back are fine. Several logging steps may go in one change, such as the check's counts and the results, as long as the read-back follows. Read it back even after an edit that succeeded: the read-back is how this skill checks the file, and later steps rely on what it shows.
